# Risk register — live project risks

Status: active. Live risk list for the hotel-mgmt MVP, owned by
`product-owner` (Closes #63), with `release-manager` input on
deployment/operations matters. Every risk carries an owner and a
mitigation or next step; the owner reviews this list at each
milestone in `docs/project/plan.md`.

| # | Risk | Owner | Mitigation / next step |
|---|---|---|---|
| R-1 | Polyglot contract discipline: the three runtimes (Go, Node.js/TypeScript, Java Spring Boot) share one monorepo under ADR-0001, so an unversioned cross-module contract change stalls integration. | Owner (decision), `architect` (contract list) | Keep versioned module APIs/events with a contract-check stage per ADR-0001; `architect` tables the contract list and `qa-lead` records the contract-guard slot. |
| R-3 | Per-hotel configuration complexity: each sale is configured per hotel without code forks, but the configuration surface (guest fields, policies, reasons, charge items, taxes, restrictions, discounts) is wide and a misconfigured hotel breaks its own desk. | `release-manager` | Keep one versioned configuration set per hotel applied identically at install and upgrade (`docs/devops/deployment.md`, section 2); validate the set against the release schema in pre-flight checks; confirm the hotel's own data at every handover. |

| R-13 | Body ceiling and server timeouts on every ingress path (#630): all eight backend services accept an unbounded request body and the three Go servers keep every timeout unset, so one oversized body or one slow peer can exhaust the single on-premise host's memory or hold a worker indefinitely — and the same change that closes that door can close it too far, refusing a legitimate desk payload or cutting a slow-but-valid call (a check-out whose completion read, or a booking whose pricing read, is still running). | `product-owner` | One ceiling for every ingress path, 65 536 bytes (64 KiB), a code constant rather than per-hotel configuration, sized from the largest existing contract fixture (`contracts/http/ModifyReservation.json`, 3 530 bytes) with more than 18× headroom, so a desk payload cannot reach it (`AC-BND-2`, `AC-BND-4`); the refusal reuses `VALIDATION_FAILED` naming `body` before any store or provider call, so a refused request writes nothing (`AC-BND-1`); the timeout values stay above the bounded provider reads a handler can wait on — the 5-second pricing client and the 2-second completion read — and are pinned by a guard per server (`AC-BND-3`, `AC-BND-5`); every service carries an at-ceiling / one-byte-over boundary guard before merge; no schema, contract, or deployment delta, so a wrong value is a single revert. |
| R-14 | Booking availability rides on a live capacity read (#631): the overbooking guard refuses when the capacity source cannot be read, so an outage of that source blocks new bookings and modifications at the desk — fail-closed by design, but a desk-visible loss of the booking function. | `product-owner` (product posture), `release-manager` (runbook) | Keep the refusal: a booking accepted against a capacity nobody verified is worse than a refused booking, and the desk shows its existing plain request-failed sentence with nothing written.
