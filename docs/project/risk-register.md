# Risk register — live project risks

Status: active. Live risk list for the hotel-mgmt MVP, owned by
`product-owner` (Closes #63), with `release-manager` input on
deployment/operations matters. Every risk carries an owner and a
mitigation or next step; the owner reviews this list at each
milestone in `docs/project/plan.md`.

| # | Risk | Owner | Mitigation / next step |
|---|---|---|---|
| R-1 | Polyglot contract discipline: the three runtimes (Go, Node.js/TypeScript, Java Spring Boot) share one monorepo under ADR-0001, so an unversioned cross-module contract change stalls integration. | Owner (decision), `architect` (contract list) | Keep versioned module APIs/events with a contract-check stage per ADR-0001; `architect` tables the contract list and `qa-lead` records the contract-guard slot. |
| R-3 | Per-hotel configuration complexity: each sale is configured per hotel without code forks, but the configuration surface (guest fields, policies, reasons, charge items, taxes, restrictions, discounts) is wide and a misconfigured hotel breaks its own desk. | `release-manager` | Keep one versioned configuration set per hotel applied identically at install and upgrade (`docs/devops/deployment.md`, section 2); validate the set against the release schema in pre-flight checks; confirm the hotel's own data at every handover. |
| R-4 | No chain design: the MVP is one installation per property with no shared data or central oversight (`NFR-DEP-1`); a buyer asking for multi-property operation has no answer and must not bend MVP boundaries early. | `product-owner` | Hold the line in scope reviews: chain work is a later direction per the system architecture (`docs/architecture/system-architecture.md`, section 4); record any chain request as a new issue instead of stretching the MVP. |
| R-5 | On-premise hardware or backup-target failure: the single host (or a cluster host) or the backup target itself fails, so the desk is down and the newest restore point may sit on the failed target. | `release-manager` | Follow the existing procedures: restart order (`docs/operations/runbook.md`, section 3), restore walkthrough (`docs/operations/runbook.md`, section 5) from the newest verified backup (`docs/operations/backup-dr.md`, sections 1 and 4); target operable again within 4 hours on equivalent hardware (`NFR-BKP-2`). |
| R-6 | Design-token propagation across the six-screen rollout (#419): one shared token or layout mistake (teal header, button colour, 44px targets, card radius, shell nav) repeats on every screen, and a wording or hotel-name-hardcoding slip in one screen PR sets the pattern for the rest. | `product-owner` | Single token source per the rollout UI contract (`docs/product/desk-ui-design-rollout.md`, sections 3–4); every screen PR is reviewed card-by-card against its design file; catalogue coverage check green and hotel-name-configurable check on each of the six PRs before merge. |
| R-7 | First-run setup-data correctness (#438): steps 2–4 write the hotel's identity, room inventory, and first owner account before the desk opens, so a bad seed or an unusable first account blocks the hotel at its first screen. | `product-owner` | Per-step validation names the missing field and persists nothing for a failing step; the wizard completes only with a working owner sign-in; steps reuse the existing config/seed/admin paths with no new endpoints; rollback is reverting the single additive PR. |
| R-8 | Shared display+API business-date ref (#503): the decided display-only format change touches a ref rendered on three screens and sent verbatim as the `businessDate` request field, so an implementation slip reformats the wire value and breaks validation, day-close, and stay/rooms reads. | `product-owner` | Spec draws the boundary before code (display formats at render, ISO stays on the wire; `AC-DSK-12`); the downstream `dev` PR updates the three render sites plus the ISO display assertions and is gated on the contract checks with no API diff. |
| R-9 | Pixel-faithful rebuild across all desk surfaces (#517): the cross-cutting visual rebuild (shell plus six screens, PrimeVue default styling abandoned wherever it diverges) can drift a token, layout, flow, or copy on one surface into the pattern for the rest, and a worker can mistake a visual rebuild for a behaviour change. | `product-owner` | One shared token source plus per-surface rebuild-vs-keep mappings (`docs/product/desk-ui-pixel-faithful-restyle.md`, sections 2–5); visual-restyle-only rule with divergences recorded per child issue for an owner decision; side-by-side screenshots plus a green design-facts gate and per-screen owner review on each of the seven child PRs (`AC-RST-8`); rollback by reverting child PRs in reverse merge order. |
| R-10 | Departure release across three services (#646): if the booking completion and the room release do not agree with the desk read, a departed booking keeps blocking same-day sale — the owner-reported defect — or the opposite split appears (booking completed while the stay is still in house, or a room reported free while a booking still blocks it), and the desk loses the visible truth that the room is saleable again. | `product-owner` | One terminal `closed` booking state (already normative in `BR-1` and the state machine), one check-out outcome that completes the booking and releases the room, and no reopen path; T2 spec with done-conditions `AC-DEP-1`..`AC-DEP-5` written before code (`docs/product/acceptance-criteria.md` section 15) and the desk delta in section 6.16; regression pins for the same-day reuse path plus the existing #588/#600/#601 guards; no schema migration or backfill on the decided path, so rollback is a single revert, and bookings already stranded in a live install are a `release-manager` operational note. |
| R-11 | Room reassignment ordering across Stay and Rooms (#647): a desk move is three calls (`AssignRoom`, `MoveRoom`, `ReleaseRoom`), so a wrong order or a missing compensation leaves one room occupied that nobody is in (the owner-reported stale hold), leaves the stay naming a room that reads free, or frees the room the guest is actually in — and a guest can then be checked into a room already in use. | `product-owner` | One documented order (assign target, move stay, release vacated room) with the target released back to ready on a refusal after its assignment and nothing released on an unreadable outcome; done-conditions `AC-REA-1`..`AC-REA-5` written before code (`docs/product/acceptance-criteria.md` section 16) and the desk delta in section 6.17 with plain-word states for every failure; guards for switch-after-preload, switch-after-commit, mid-stay, and the partial-failure ordering, plus the existing #586/#588/#600/#601/#646 pins; no new operation or migration on the decided path, so rollback is a single revert, and rooms already stranded are a `release-manager` operational note. |
| R-12 | Booking register read fan-out and nav density (#648): the new read-only desk screen completes every row through its own `GetReservation` (up to the 50-row cap) on top of the calendar, room-type, in-house, and occupied-room reads, so a wide range on a busy calendar turns one screen load into dozens of reads; the same change adds a ninth shell tab, so a label or width slip pushes the header past the `1200px` content width in one locale and reads as a broken desk. | `product-owner` | The range defaults to seven nights and the list is capped at 50 rows with one plain narrow-the-dates sentence, so the fan-out is bounded by design rather than by luck; the tab label is the short noun form, the first implementation PR carries 1200px evidence in both locales, and an overflow is an owner decision between a shorter label and a shell rule change — never a silent truncation; the screen is read-only over existing operations, so rollback is a single revert, and a measured slowdown is the recorded trigger for a `ListReservations` follow-up (`docs/product/booking-management-view.md` section 12, G2). |

| R-13 | Body ceiling and server timeouts on every ingress path (#630): all eight backend services accept an unbounded request body and the three Go servers keep every timeout unset, so one oversized body or one slow peer can exhaust the single on-premise host's memory or hold a worker indefinitely — and the same change that closes that door can close it too far, refusing a legitimate desk payload or cutting a slow-but-valid call (a check-out whose completion read, or a booking whose pricing read, is still running). | `product-owner` | One ceiling for every ingress path, 65 536 bytes (64 KiB), a code constant rather than per-hotel configuration, sized from the largest existing contract fixture (`contracts/http/ModifyReservation.json`, 3 530 bytes) with more than 18× headroom, so a desk payload cannot reach it (`AC-BND-2`, `AC-BND-4`); the refusal reuses `VALIDATION_FAILED` naming `body` before any store or provider call, so a refused request writes nothing (`AC-BND-1`); the timeout values stay above the bounded provider reads a handler can wait on — the 5-second pricing client and the 2-second completion read — and are pinned by a guard per server (`AC-BND-3`, `AC-BND-5`); every service carries an at-ceiling / one-byte-over boundary guard before merge; no schema, contract, or deployment delta, so a wrong value is a single revert. |
| R-14 | Booking availability rides on a live capacity read (#631): the overbooking guard refuses when the capacity source cannot be read, so an outage of that source blocks new bookings and modifications at the desk — fail-closed by design, but a desk-visible loss of the booking function. | `product-owner` (product posture), `release-manager` (runbook) | Keep the refusal: a booking accepted against a capacity nobody verified is worse than a refused booking, and the desk shows its existing plain request-failed sentence with nothing written. The read reuses the wired service-dependency pattern (boot wiring plus each service's health endpoint), the runbook's restart order covers the source, and a capacity-specific refusal sentence or an alert is a follow-up, not a silent fallback to the request's number. |
| R-16 | Money ceiling in the Billing adapters (#635): the adapter that turns a JSON number into a stored minor-unit amount truncates a fractional value and bounds no magnitude, so a caller can post `12.99` as 12 or push a value past the exact-integer range of a `double` — and the fix can overshoot the other way, refusing a legitimate large charge (one room charge at a 730-night stay's frozen quoted total) as if it were nonsense. | `product-owner` | One ceiling for every money adapter, 1 000 000 000 000 minor units, derived from the longest stay Rates accepts (730 nights) times the owner boards' nightly rate with more than 15× headroom, and four orders of magnitude below 2<sup>53</sup> so every accepted amount stays exact (`AC-AMT-2`, `AC-AMT-3`); the ceiling is a code constant, not per-hotel configuration, and the refusal reuses `VALIDATION_FAILED` naming the field in the adapter before any service or folio call (`AC-AMT-1`); the service-level sign rules and the 0–100 percent range are untouched (`AC-AMT-4`); each adapter carries a fractional guard, an over-ceiling guard, and an at-ceiling / one-over boundary pair before merge (`AC-AMT-5`); no schema, contract, or deployment delta, so a wrong number is a single revert. |
| R-17 | Report window span in Reporting (#641): `parseRange` bounds a report window's shape and order but not its span, and both range reports then loop over every date under the store mutex, so one wide window (`0001-01-01`..`9999-12-31`) stalls every other report — and the same guard can close too far, refusing a legitimate long look-back (the owner's two-year reporting need). | `product-owner` | One span cap for both range reports, 730 nights (731 inclusive dates), adopted from the two-year window `NFR-PERF-2` documents and from the number Rates already uses for a stay range (`services/rates/internal/store/store.go:254`), so the cap admits the whole documented look-back and refuses only what is wider than it; the refusal reuses `VALIDATION_FAILED` naming `dateTo` before the store lock (`AC-RPT-5`), a window at the cap returns exactly today's rows (`AC-RPT-6`), the cap is a code constant with no schema, contract-operation, or deployment delta (`AC-RPT-7`), and each operation carries an over-cap guard, an at-cap guard, and the one-night-past boundary before merge, so a wrong number is a single revert. |

| R-18 | Guest identity reads and payload bounds in Guests (#640): the name lookup resolves duplicates by first match, so the desk can open the wrong profile, stay links, preferences, and notes — and tightening it can overshoot the other way, refusing a desk flow that relied on first-match, because a live hotel may already hold two guests with the same full name and has no merge or distinguish flow; a wrong shape or length bound can also refuse a legitimate contact detail, preference, or note. | `product-owner` | The refusal is the ambiguity itself, not a guess: `VALIDATION_FAILED` naming `fullName` with the match count and no profile returned, while a unique name and every `guestId` read answer exactly as today (`AC-GID-1`, `AC-GID-2`); the bounds are taken from the largest existing fixtures with more than nine times headroom — a 16-field object of short string, number, or boolean values and a 2 000-character note — and sit far under the 64 KiB body ceiling from #630 (`AC-GID-3`, `AC-GID-4`); they are code constants, apply to writes only with reads unchanged, and carry at-bound and one-over guards in both stores plus the regression guards (`AC-GID-7`); the desk says the ambiguity in plain words in both locales instead of the generic retry sentence (`AC-GID-6`); no schema migration, contract token, or backfill, so a wrong number or an over-strict shape is a single revert, and a live install's duplicate names are the trigger for the recorded merge/distinguish follow-up rather than a reason to keep the first match. |
