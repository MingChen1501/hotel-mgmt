# Risk register — live project risks

Status: active. Live risk list for the hotel-mgmt MVP, owned by
`product-owner` (Closes #63), with `release-manager` input on
deployment/operations matters. Every risk carries an owner and a
mitigation or next step; the owner reviews this list at each
milestone in `docs/project/plan.md`.

| # | Risk | Owner | Mitigation / next step |
|---|---|---|---|
| R-1 | Polyglot contract discipline: the three runtimes (Go, Node.js/TypeScript, Java Spring Boot) share one monorepo under ADR-0001, so an unversioned cross-module contract change stalls integration. | Owner (decision), `architect` (contract list) | Keep versioned module APIs/events with a contract-check stage per ADR-0001; `architect` tables the contract list and `qa-lead` records the contract-guard slot. |
| R-3 | Per-hotel configuration complexity: each sale is configured per hotel without code forks, but the configuration surface (guest fields, policies, reasons, charge items, taxes, restrictions, discounts) is wide and a misconfigured hotel breaks its own desk. | `release-manager` | Keep one versioned configuration set per hotel applied identically at install and upgrade (`docs/devops/deployment.md`, section 2); validate the set against the release schema in pre-flight checks; confirm the hotel's own data at every handover. |
| R-4 | No chain design: the MVP is one installation per property with no shared data or central oversight (`NFR-DEP-1`); a buyer asking for multi-property operation has no answer and must not bend MVP boundaries early. | `product-owner` | Hold the line in scope reviews: chain work is a later direction per the system architecture (`docs/architecture/system-architecture.md`, section 4); record any chain request as a new issue instead of stretching the MVP. |
| R-5 | On-premise hardware or backup-target failure: the single host (or a cluster host) or the backup target itself fails, so the desk is down and the newest restore point may sit on the failed target. | `release-manager` | Follow the existing procedures: restart order (`docs/operations/runbook.md`, section 3), restore walkthrough (`docs/operations/runbook.md`, section 5) from the newest verified backup (`docs/operations/backup-dr.md`, sections 1 and 4); target operable again within 4 hours on equivalent hardware (`NFR-BKP-2`). |
| R-6 | Design-token propagation across the six-screen rollout (#419): one shared token or layout mistake (teal header, button colour, 44px targets, card radius, shell nav) repeats on every screen, and a wording or hotel-name-hardcoding slip in one screen PR sets the pattern for the rest. | `product-owner` | Single token source per the rollout UI contract (`docs/product/desk-ui-design-rollout.md`, sections 3–4); every screen PR is reviewed card-by-card against its design file; catalogue coverage check green and hotel-name-configurable check on each of the six PRs before merge. |
| R-7 | First-run setup-data correctness (#438): steps 2–4 write the hotel's identity, room inventory, and first owner account before the desk opens, so a bad seed or an unusable first account blocks the hotel at its first screen. | `product-owner` | Per-step validation names the missing field and persists nothing for a failing step; the wizard completes only with a working owner sign-in; steps reuse the existing config/seed/admin paths with no new endpoints; rollback is reverting the single additive PR. |
| R-8 | Shared display+API business-date ref (#503): the decided display-only format change touches a ref rendered on three screens and sent verbatim as the `businessDate` request field, so an implementation slip reformats the wire value and breaks validation, day-close, and stay/rooms reads. | `product-owner` | Spec draws the boundary before code (display formats at render, ISO stays on the wire; `AC-DSK-12`); the downstream `dev` PR updates the three render sites plus the ISO display assertions and is gated on the contract checks with no API diff. |
| R-9 | Pixel-faithful rebuild across all desk surfaces (#517): the cross-cutting visual rebuild (shell plus six screens, PrimeVue default styling abandoned wherever it diverges) can drift a token, layout, flow, or copy on one surface into the pattern for the rest, and a worker can mistake a visual rebuild for a behaviour change. | `product-owner` | One shared token source plus per-surface rebuild-vs-keep mappings (`docs/product/desk-ui-pixel-faithful-restyle.md`, sections 2–5); visual-restyle-only rule with divergences recorded per child issue for an owner decision; side-by-side screenshots plus a green design-facts gate and per-screen owner review on each of the seven child PRs (`AC-RST-8`); rollback by reverting child PRs in reverse merge order. |
| R-10 | Departure release across three services (#646): if the booking completion and the room release do not agree with the desk read, a departed booking keeps blocking same-day sale — the owner-reported defect — or the opposite split appears (booking completed while the stay is still in house, or a room reported free while a booking still blocks it), and the desk loses the visible truth that the room is saleable again. | `product-owner` | One terminal `closed` booking state (already normative in `BR-1` and the state machine), one check-out outcome that completes the booking and releases the room, and no reopen path; T2 spec with done-conditions `AC-DEP-1`..`AC-DEP-5` written before code (`docs/product/acceptance-criteria.md` section 15) and the desk delta in section 6.16; regression pins for the same-day reuse path plus the existing #588/#600/#601 guards; no schema migration or backfill on the decided path, so rollback is a single revert, and bookings already stranded in a live install are a `release-manager` operational note. |
| R-11 | Room reassignment ordering across Stay and Rooms (#647): a desk move is three calls (`AssignRoom`, `MoveRoom`, `ReleaseRoom`), so a wrong order or a missing compensation leaves one room occupied that nobody is in (the owner-reported stale hold), leaves the stay naming a room that reads free, or frees the room the guest is actually in — and a guest can then be checked into a room already in use. | `product-owner` | One documented order (assign target, move stay, release vacated room) with the target released back to ready on a refusal after its assignment and nothing released on an unreadable outcome; done-conditions `AC-REA-1`..`AC-REA-5` written before code (`docs/product/acceptance-criteria.md` section 16) and the desk delta in section 6.17 with plain-word states for every failure; guards for switch-after-preload, switch-after-commit, mid-stay, and the partial-failure ordering, plus the existing #586/#588/#600/#601/#646 pins; no new operation or migration on the decided path, so rollback is a single revert, and rooms already stranded are a `release-manager` operational note. |
